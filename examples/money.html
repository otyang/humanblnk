The situation

Ada types "50,000" to top up in naira, "0.00012345" to buy bitcoin, and "20.5" to send USDT. Oja must store each one exactly, never as a float, and show it back in a form she can read and spend. ledger.Money carries all of that.

The three forms of an amount

FieldExample for 0.456 BTCWhat it is
Value"0.456"the human decimal, trailing zeros trimmed
PreciseAmount45600000the integer in the smallest unit, a *big.Int. Blnk sums this on balances
Precision100000000the multiplier: Value × Precision = PreciseAmount
Display"0.456"for people to read, set on every Money the library returns, including from Parse, Precise and ParseDecimal. Never compute with it

Only precise_amount and precision are sent to Blnk, never its float amount, so 0.456 can't turn into 0.45599999.

Amount and Parse

Amount keeps the text and upper-cases the currency. It doesn't resolve anything, so PreciseAmount is still nil. Every call that takes a Money resolves it with the currency's precision. svc.Parse does the same now, so you can read both forms and Display.

  • String() gives "0.456 BTC". Fixed() gives every decimal place the precision allows.
  • IsZero(), Sign() and IsPositive() compare without floats. Sign and IsPositive need a resolved amount.

Commas, zeros and precision by currency

  • Commas and underscores are dropped, so "1,500.50" is 150050 kobo.
  • JPY has no decimals and KWD has three: the precision follows the currency, not a fixed two places.

Integers you already hold

Minor leaves Precision and Display empty, and the call fills them from the currency. Precise and ParseDecimal set everything up front. Their Display follows the built-in rule for the currency, because they have no Service to read Config.Currencies from. A Money that carries a different precision from the currency's is converted with its value kept, or refused if it has more decimals than the currency allows. It is never posted at the wrong scale.

Rejected amounts

More decimal places than the currency allows, exponents, anything that isn't a number and an empty amount fail with ErrInvalidInput before anything is sent to Blnk. Nothing is rounded for you.

Fees: an empty currency

A fee is always in the transaction's currency. Write it with an empty currency and it takes the amount's.

  • ledger.NoFee is a zero fee. Use it for a free transaction when Config.Fees isn't set.
  • A fee in another currency is refused. For an exchange, the fee is in the sell currency. See Fees.
  • The deposit records the gross amount; meta_data.fee and meta_data.net_amount hold the split.

JSON

Money marshals to both forms plus the display string. precise_amount is a string so JavaScript clients don't lose digits on 18-decimal assets.

  • On the way in, amount may be a string ("0.1") or a bare number (0.1). A number is read from its literal text, never through float64.
  • currency is upper-cased. precise_amount and precision are optional. When both amount and precise_amount are given, they must agree.
  • display is ignored on the way in.

Display

Display is cut, never rounded up, so a displayed balance can always be spent in full. The exact amount stays in Value.

Every currency has a display rule. Fiat shows every decimal place its precision has, padded; crypto trims trailing zeros; stablecoins read as money:

CurrencyRuleExample
Fiatevery decimal place of its precision, padded100.50 USD, 5000 JPY, 1.250 KWD
USDT, USDC, DAI2 places, padded20.50
BTC, LTC, BCH, DOGEup to 8 places, trailing zeros dropped0.5
ETH, BNB, POL, TRX, XRP, ADAup to 6 places, trailing zeros dropped0.123456
SOLup to 4 places, trailing zeros dropped1.25

Change any of them with Config.Currencies. Only the fields you set change, so {Code: "ETH", Display: ...} keeps ETH's name, symbol and precision.

DisplayRule fieldWhat it changes
Decimalsthe most decimal places shown, capped at the currency's precision
TrimZerosdrop trailing zeros instead of padding to Decimals
A zero Display means "keep the built-in rule". To show whole units only, write DisplayRule{Decimals: 0, TrimZeros: true}, as for NGN above.

Currencies: svc.Currency and svc.Currencies

humanblnk knows 179 currencies without any configuration: every current ISO 4217 code, plus BTC, ETH, SOL, TRX, LTC, BCH, XRP, ADA, DOGE, BNB, POL and the stablecoins USDT, USDC and DAI. Each has a code, a name, a symbol, a kind (ledger.Fiat, ledger.Crypto or ledger.Stablecoin), a precision and a display rule. The built-in list is ledger.Currencies.

Read them through the Service, which also sees what Config.Currencies changed. Use them to fill a currency picker, or to show a balance with its name and symbol.

  • Balances don't carry the name or symbol: look them up with svc.Currency(acct.Currency).
  • svc.Currencies() returns them all; pass kinds to filter. The list is sorted by code.
  • Fiat precisions are the ISO 4217 minor units: 100 for NGN and USD, 1 for JPY and XOF, 1000 for KWD. Crypto precisions are the chain's smallest unit: 100000000 for BTC (satoshi), 10¹⁸ for ETH (wei).

Adding and changing currencies: Config.Currencies

Each precision must be a power of 10. A new code needs Precision; its Kind defaults to ledger.Fiat and its display to every decimal place, padded.

Keep a currency's precision fixed once money has moved. Blnk sums precise_amount on balances, so mixing precisions corrupts the totals.

Unknown currencies

A code that is neither built in nor in Config.Currencies is refused with ErrInvalidInput when opening accounts and parsing amounts, so a typo can't open an account. Set Config.UnknownCurrency: ledger.AllowUnknown to accept any code at Config.DefaultPrecision (default 100).

Configuration mistakes

Mistakes in Config.Currencies don't stop ledger.New. The bad entries are left out and svc.Check reports all of them, so call it at start-up.
