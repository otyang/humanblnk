Wallets and financial operations on Blnk

A practical guide to humanblnk, the domain layer between your product and Blnk, told through Oja, a wallet business in Nigeria: naira, dollars and bitcoin, from a customer’s signup to the finance team’s month-end close.

By Otyang · github.com/otyang/humanblnk · Detailed examples for every use case

Overview

humanblnk is a wallet and financial-operations domain layer for Go, built on top of Blnk, the open-source double-entry ledger.

A wallet business has two jobs. It moves its customers’ money: sign-ups, top-ups, transfers, card payments, withdrawals, refunds. And it runs its own books: fees earned, money held by payment providers, settlements, unmatched payments, corrections, month-end close. Blnk is the ledger underneath both, and deliberately knows nothing about either: it has no idea what a customer, a fee, a KYC limit, a frozen account or a settlement is. humanblnk is the layer that does. Your app calls it in the business’s own words; it applies the business rules and turns each call into correct Blnk entries.

This guide follows Oja, a Nigerian wallet business. Ada keeps naira, dollars and bitcoin with Oja, pays friends and merchants, and saves for rent. Chidi Stores sells through Oja's marketplace. Oja's finance team settles with Paystack, matches stray payments and closes the books. Every code sample on this page is compiled and run against the library's test suite.

The interface has one handle per domain, and each handle's methods live in the files with its prefix (wallet_*.go, ops_*.go; shared code is in core_*.go):

HandleForFiles
l.Wallet()what customers do: open accounts, add money, pay, cash out, hold, save, buy, disputewallet_*.go
l.Ops()what the business does: provision ledgers, freeze and close, run its own accounts, settle with providers, match unknown money, correct, prove the books, reconcileops_*.go

Hand each part of your application only the handle it needs. A customer-facing server that gets a ledger.Wallet can’t freeze or close accounts, adjust balances or record settlements: those methods aren’t on it.

What a domain layer is

The business rules between your product and the ledger.

Every wallet built on Blnk needs the same code between the product and the ledger: check the account isn’t frozen, check the customer’s limit, price the fee, split the payment into its entries, hold it until the provider answers, refuse a second approval by the same person. That code is the domain layer: it knows the business, where Blnk knows the bookkeeping. humanblnk is that layer, written once and tested against real Blnk Core.

Knows aboutscreens, sessions, providers’ APIs, KYC checkscustomers, accounts, fees, limits, holds, disputes, settlements, house accountsbalances and transactions
Decideswhat the customer asked for, and whenwhether it’s allowed, what it costs, which entries it becomeswhether the entries balance and the money is there
Storesyour own users and recordsnothing of its own: everything lives in Blnkevery balance and entry

One withdrawal, through the layers

LayerWhat happens
1Your appAda taps “Withdraw ₦20,000 to GTBank”. The app makes a reference once, shows wallet.QuoteWithdraw, and calls wallet.Withdraw when she confirms.
2humanblnkRefuses if her account or its ledger is frozen or closed, or she is over her tier’s limit. Prices the fee with your Config.Fees (₦50 here). Builds the entries: Ada → @FlutterwaveClearing ₦20,000 and Ada → @FeeIncome ₦50, held inflight for at most 24 hours.
3Blnk CoreChecks ₦20,050 is available, reserves it and returns the inflight transaction.
4Your appCalls Flutterwave with the transaction id as the reference.
5Your app → humanblnkFlutterwave’s webhook: SUCCESSFUL → wallet.Confirm; FAILED → wallet.Cancel, and the money is Ada’s again.
6humanblnk → BlnkCommits or voids the transaction. A confirm is retried only when Blnk certainly didn’t act, so it can’t post twice.
7Finance, laterops.RecordSettlement clears @FlutterwaveClearing against the bank when Flutterwave settles; ops.TrialBalance proves the books still add up.

What humanblnk is not

  • Not a ledger. It stores nothing itself; Blnk is the record. It can be restarted or scaled out without losing a cent.
  • Not a payment gateway. It never calls Paystack, Flutterwave or a bank. Your app does, and tells humanblnk what happened.
  • Not a KYC system. You decide a customer’s tier; humanblnk applies the limits you set for it.
  • Not a full Blnk SDK. The blnk package covers what the domain needs. Anything else you call on Blnk directly, and then the domain rules don’t apply to it.

Blnk gives you primitives and leaves the rules to you. These are the rules humanblnk owns, so every app built on it gets them the same way:

Ledgers, customer accounts and house accounts each have their own id type: LedgerID, AccountID and HouseRef. passing a ledger id to ops.FreezeAccount doesn’t compile; a plain string converted to the wrong type is refused at run time with ErrWrongKind, before anything is written.

Install and run Blnk

You need Blnk Core 0.15.4 or later, self-hosted or on Blnk Cloud. Every release is tested against Core 0.15.6 and 0.15.4.

Import the module root for everything in one place, or the packages directly. They are the same types, so mix them freely; this guide uses ledger.

Locally, Blnk Core runs in Docker (server, worker, Postgres, Redis) and listens on http://localhost:5001; see Blnk's install guide. To try the library first with no setup at all, run the bundled walkthrough against the in-memory emulator:

Set up the service

Account and ledger status are always enforced: every movement reads the customer accounts it touches (one extra request each) and refuses frozen, blocked or closed ones, and money leaving a frozen ledger. Blnk itself ignores status, so this is what makes Freeze and Close mean something.

Create one Service at startup and share it; it is safe for concurrent use. Depend on the ledger.Ledger interface, or on just ledger.Wallet or ledger.Ops, in the rest of your code. Check confirms at startup that the client is configured correctly, Core is up and reaches its database, and LedgerID exists.

Then take the two handles, one per domain:

SettingWhat it does
LedgerIDThe Blnk ledger customer accounts are opened in. It must exist: call svc.Check(ctx) at startup to find out now. See Ledgers.
FeesPrices every chargeable call that doesn’t set Fee itself. See Fees.
Limits, LocationPer-tier spending caps and the time zone their days reset in. See Limits.
LedgerStatusTTLHow long a ledger’s frozen/active status is cached (default 30s). A freeze made by another process applies here within this time.
DisplayHow amounts are shown per currency. See Money.
PrecisionsSmallest unit per currency. Built in for fiat and major crypto; never change once money has moved.
WithdrawalHoldTTLPending withdrawals cancel themselves after this (default 24h).
UseQueueRoute writes through Blnk’s queue for very hot balances; results then arrive by webhook.
FeeIncomeAccount, …Rename house accounts if you already have money on other indicators.

Blnk Cloud

The same library against a Core hosted by Blnk.

On Blnk Cloud you call Blnk’s proxy with a Cloud API key; every request carries your instance_id. A proxy URL without an instance ID, or one that doesn’t start with instance_, is a configuration error that Check reports. For every client, self-hosted or Cloud, redirects to another host or from https to http are refused, so your API key never leaves the host you configured.

Provision ledgers

One ledger per market, created once however many times provisioning runs.

Blnk has no idempotency for ledgers and doesn’t require unique names, so ops.CreateLedger provides it: it looks for a ledger carrying your Key first and returns that one with Replayed set. The same key with a different name is ErrDuplicateReference. Calls in one process with the same key run one at a time; if two processes still race and both create, the oldest ledger wins everywhere and the other is marked duplicate, which wallet.OpenAccount refuses. Create ledgers when you provision, not on the request path.

wallet.OpenAccount checks the ledger exists before opening anything (ErrLedgerNotFound otherwise), and never opens customer accounts in Blnk’s general ledger, where house accounts live.

Money

Amounts are typed as decimal strings, exactly as the user entered them, and never pass through floating point. Every amount the service returns carries three forms:

FieldExample (₦1,250.5)Use it for

PreciseAmount + Precision125050 × 100what Blnk stores: the integer in the smallest unit

References and retries

Every movement takes a Reference, and Blnk accepts each reference once. That makes every call safe to retry: send the same request again and you get the original transaction back with Replayed: true instead of moving money twice.

  • Generate the reference once, when the user taps "Send", and store it with the pending request, so a retry after a timeout reuses it.
  • For money arriving from a provider, use the provider’s reference (Paystack’s, a blockchain txid:vout), so a repeated webhook can’t credit twice.
  • The same reference with a different amount, account or kind of movement fails with ErrDuplicateReference: a real conflict to investigate, not to retry.
  • wallet.Confirm and Cancel carry no reference, so the client never repeats them blindly after a timeout: look the transaction up before trying again.

Accounts and the chart of accounts

Customer accounts are where users’ money lives; they sit in your own ledgers. House accounts, the business’s own (“house” is the business itself), named with @, are the other side of every entry and are what finance reconciles. Blnk creates each house account on first use, per currency, in its general ledger. The table is ledger.Chart; add your own indicators to it at startup.

AccountTypeNormalRole

Blnk debits the source and credits the destination, so asset and expense accounts run negative and liability, income and equity accounts run positive. House accounts are their own type, HouseAccount, read through ops.GetHouseAccount and ops.ListHouseAccounts: it carries the account’s Type and Normal side from ledger.Chart, and Natural, the balance on its normal side, so an asset that is owed to you reads positive. Provider clearing accounts default to assets; add a payout-only provider to Chart as a liability if you prefer. Customer accounts are Account, whose Kind is customer, pot or escrow.

Onboard a customer

Ada signs up and gets naira, dollar and bitcoin accounts in one call.

This creates a Blnk identity and one account per currency. With ExternalID set (your own user id), calling it again after a timeout returns the same accounts and opens any new currencies, so signup is safe to retry. The tier metadata drives limits and pricing.

Read a balance

Available is what the app should let Ada spend: the balance minus money reserved by card holds and pending withdrawals.

Statements

A downloadable month for Ada, checked against the ledger.

ops.HouseStatement builds the same statement for a house account such as @FeeIncome. The statement lists posted entries only, dated by when they took effect, so a standing order appears on the day it posted. The closing balance is checked against Blnk’s own balance at the end of the period: a statement that doesn’t add up is an error, never a wrong document. Fees appear as their own lines, as on a bank statement.

Exchange currency

QuoteExchange shows the amounts, fee and balance after, with Blnk dry-running both legs, before anything moves. Give Buy instead of Sell to land an exact amount (“receive exactly ₦100,000”). The bought amount rounds down and a computed sell amount rounds up, so rounding never costs you.

Crypto

Exact satoshi accounting, with display that never overstates a balance.

Crypto uses each chain’s smallest unit (satoshi, wei), so ledger balances match the chain exactly. For stablecoins on several chains, note that decimals differ by chain (USDT is 6 on Tron and Ethereum, 18 on BNB Chain): keep one precision per ledger currency and convert at the edge, or give each chain its own currency code.

Each escrow is its own account, so what’s still held is simply its balance, and Blnk itself refuses to release more than is left.

Disputes and chargebacks

Freeze the disputed money until the case is decided.

Opening a dispute places a hold in the seller’s account pointed back at the payer, so the money can’t be spent while it is investigated. For a payment that carried a fee, the library disputes the leg that paid the seller, never the fee.

Refunds

Return part of a payment when an item is out of stock.

Partial refunds are linked to the original with meta_data.refund_of, and they are added up before each new one, so over-refunding is refused, and a retried refund replays instead of counting twice. A transaction can be reversed in full with Refund or in parts with RefundPartial, not both. If refunds for the same transaction can run concurrently, serialise them (one worker or a row lock).

Savings pots and standing orders

Ada saves for rent automatically every month.

A pot is a sub-account in the same currency and identity, with an optional goal. Blnk has no native recurrence, so a standing order is a set of scheduled transfers sharing meta_data.recurring_reference; calling Schedule again with the same input is safe.

Payroll

A merchant pays its staff in one batch.

Atomic makes the batch all-or-nothing. Up to 10,000 transfers per batch; Async processes in the background with the outcome sent as a bulk_transaction.* webhook.

Fees

Every chargeable call (deposit, withdrawal, transfer, exchange, standing order, bulk item and their quotes) must say what it charges, so a fee can never be forgotten. Either pass Fee on the call (ledger.NoFee for free), or set Config.Fees to price them centrally:

FeeRuleExampleMeaning
Percent"1.5"1.5% of the amount
Fixed"10"flat ₦10 (in the transaction’s currency)
Min, Max"10", "2000"floor and cap
Tiers≤ ₦5,000: ₦10, above: 0.1%bands by amount
RoundingRoundHalfUpor RoundUp / RoundDown

A fee is always in the transaction’s own currency. To price “$0.50 everywhere”, convert inside your function with r.Convert(ledger.Amount("0.50", "USD"), rate, ledger.RoundUp). A fee passed on the call always wins over the function, which is how promotions and waivers work.

Limits and KYC tiers

Per-tier caps, checked before any money moves.

Limits apply to money leaving customer accounts: transfers, withdrawals, holds, splits, exchanges and escrow (bulk batches are not checked). A pending hold counts while held and comes back if cancelled. Days and months reset in Config.Location.

Trial balance

One call to prove the books add up.

In double entry every currency nets to zero. Run this nightly and alert when Balanced is false; CustomerFunds is the total you owe customers, the figure your safeguarding account must cover. House lists every house account as a HouseAccount, with its type and Natural balance.

Provider settlement

Clear Paystack’s receivable when the money reaches your bank.

Each provider has its own clearing account, so after recording settlements its balance is exactly what that provider still owes you (or you owe it) and can be ticked off against its report. Use SettlementPayout for payout providers you prefund.

Unidentified money

Hold money you can’t match yet; claim it for its owner once support knows whose it is, or return it to the provider.

Manual corrections

Corrections with a second pair of eyes.

Every adjustment records its reason, requester and approver in metadata, and the same person can’t do both.

Balance alerts

Get told when a float runs high or low.

Watch a house account with House, as here, or a customer account with AccountID; set one, not both.

Reconciliation

Match Paystack’s report against the ledger.

Without RuleIDs, a rule matching reference, currency and amount exactly is created once and reused. Up to 10,000 records go inline; larger exports upload as a CSV with File. Blnk reports counts, not the matched lines.

Payments that carried a fee are stored by Blnk as legs (ref-1, ref-2), so they don’t match a provider line one-to-one. Try Strategy: "one_to_many" with GroupingCriteria: "parent_transaction", and check the counts against your own Core version before relying on them.

Freeze and close

A whole ledger can be frozen too. Then no money can leave any of its customer accounts, while deposits into them and postings to house accounts carry on:

ops.CloseAccount is final: a closed account is never reopened (open a new one). It needs a Reason, a RequestedBy and an ApprovedBy who is someone else, and refuses while anything is pending or scheduled, while a pot under the account is open, or while an escrow it pays into or out of still holds money. Then it moves any remaining balance to SweepTo and marks the account closed. A frozen account can still be closed, but nothing can be swept out of a frozen ledger, and a closed account can’t be frozen or unfrozen. Money sent to a closed account later (a late provider refund, say) is refused with ErrAccountClosed; hold it with HoldInSuspense, then claim it for the customer’s new account or return it to the provider.

Each Service caches a ledger’s status for Config.LedgerStatusTTL (30 seconds by default), so a freeze made by another process applies within that time. Pending transactions created before the freeze can still be confirmed.

Webhooks

React to what happens in the ledger.

balance.created sets e.Account for a customer account and e.House for a house account. With Secret set, signatures (X-Blnk-Signature, HMAC-SHA256 of timestamp.body) and a five-minute timestamp window are checked; without it nothing is verified, so make sure it is set in production. Blnk delivers at least once and retries on errors, so make handlers idempotent, for example keyed on e.Receipt.TransactionID plus e.Name. An expired hold arrives as transaction.void.

Logging, metrics and tracing

Observer receives every call’s name, context and error, which is all you need for metrics or one OpenTelemetry span per call. Business refusals (insufficient funds, limits) log at Warn, failures at Error.

Testing your app

Fast tests with no Docker, using the real request code.

ledgertest is an in-memory Blnk Core: your tests run the real Service code, so they exercise the same requests production sends. ledgertest.New creates a ledger for the test and sets Config.LedgerID to it. It behaves like Core 0.15 where that matters (fee legs, stored ids, required descriptions) and lets you move time forward to expire holds and run scheduled transfers. Blnk versions and known limits

Blnk Core
Minimum0.15.4: dry run (0.15.3) for every quote, and the current error codes
Tested on0.15.6 and 0.15.4, built from source in CI with Postgres 16 and Redis 7

Core before 0.15.3 ignores dry_run and would post a quoted transaction, so it isn’t supported.

  • Fee legs. A movement with a fee is stored as legs (ref-1, ref-2) with no parent record. The library rebuilds the parent for lookups and retries, and disputes or refunds pick the recipient’s leg, but raw Blnk queries and reconciliation see legs. A pending one is confirmed in full (or one leg at a time), never partially.
  • House account ids. Blnk stores @FeeIncome-style accounts by balance id; receipts and history show the id, statements show the name. Read them through ops.GetHouseAccount; wallet.GetAccount refuses them.
  • Ledger keys. Blnk has no unique ledger names, so two processes creating the same Key at once can both succeed; the oldest then wins and the other is marked duplicate. Create ledgers at provisioning time.
  • Account and ledger status are enforced by this library, not by Blnk, so movements Blnk posts by itself (scheduled transfers, auto-capture, hold expiry) and calls made to Blnk directly aren’t checked. Each process caches a ledger’s status for LedgerStatusTTL.
  • Concurrent partial refunds of one transaction can both pass the remaining-amount check; serialise them.
  • Balance alerts fire after every update while the condition holds; debounce them.
