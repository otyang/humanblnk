Testing your service

Scenario: the airtime service from chapter 7 needs tests that run on every go test: on a laptop, in CI, with no Blnk, Docker or network.

humanblnktest starts an in-memory Blnk for each test and gives you a humanblnk.Client on it. Your code runs exactly as in production: the same humanblnk, the same Blnk client, the same rules, against a Blnk that lives in the test's memory and disappears when it ends.

How close is it to Blnk?

The in-memory Blnk copies the Blnk Core 0.15.6 behaviour humanblnk relies on:

  • System accounts (@World, @FeeIncome, clearing accounts) are made the first time a transaction names them.
  • A reused reference is refused, so ErrDuplicate and ErrReferenceUsed come back as they would.
  • A split is held a posting at a time. If a later posting fails, the earlier holds are released at once, as Blnk does.
  • Holds stay INFLIGHT; captures and releases are transactions of their own.
  • Watches fire balance.monitor: humanblnktest.WithWebhook(url, secret) sends signed webhooks to your handler, so VerifyWebhook can be tested end to end. Delivery is best effort and gives up after 5 seconds, so a handler must answer rather than block (say, on a full channel).

humanblnk's contract tests run against both the in-memory Blnk and a real one, so a difference in what they cover fails CI. Where they don't look, it isn't Blnk:

  • Nothing is ever queued: every write applies at once, and queued balances are always 0.
  • Hold expiry happens on the first request after it, to the second.
  • Splits take exact amounts (precise_distribution) only, and a batch can't hold a split. Batches, commits and voids can't be previewed.
  • effective_date and backdating are ignored.
  • Reconciliation matches one_to_one only.

humanblnk itself uses none of these, but a raw blnk.Client on hb.URL could.

Options

OptionFor
WithCustomerLedger("Savings")another customer ledger; its id is hb.CustomerLedgers["Savings"]
WithRollbackDelay(d)how long a split or batch applied directly (not through humanblnk) stays before Blnk's refund
WithWebhook(url, secret)send Blnk's webhooks to a test server
WithClientOptions(...)pass options to humanblnk.New, such as WithAccountCacheSize

Keep a test against a real Blnk too, for the behaviour your service relies on most: a few in CI with docker compose -f deploy/docker-compose.yml up -d cost little and catch what no fake can.
